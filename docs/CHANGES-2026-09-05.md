# Changes — 2026-09-05

> Domain verification, Test Mode, and the onboarding surface.
> What changed, why, where it landed, and what it is verified by.

**Scope:** documentation, database, API, and web app.
**Status:** implemented, typechecked, unit- and integration-tested.
**Supersedes:** the decisions listed in §6.

---

## 1. Why this revision exists

Two problems, one of them invisible until it is named.

**The visible one.** The specification described the website-verification
method two mutually exclusive ways (a file at a fixed path, and a `<meta>` tag),
named the DNS record two different things, and disagreed with itself about
whether deleting a domain was reversible. An implementer working from one
document would have built something that could not interoperate with an
implementer working from another.

**The invisible one.** There was no way to exercise any of it. Verification
depends on real DNS propagation and a publicly reachable website — neither of
which exists in CI, on a laptop, or for a business owner evaluating the product
before they involve their web developer. The previous decision (D-04) rejected
any bypass on the grounds that a real staging subdomain would suffice. That
framed it as a testing inconvenience. It is not: **it is a product gap.** A
prospect who does not yet control a domain could not reach the end of the
funnel at all.

This revision resolves the contradictions and closes the gap — without
softening the real verification path by a single conditional.

---

## 2. The headline change: Test Mode

A third verification method, `SANDBOX`, available **in production**, that
verifies instantly and grants nothing.

It works because of what it accepts, not who asks. The eligible set is exactly
the set of names **nobody can register** — `*.test`, `*.example`, `*.invalid`,
`*.localhost`, `*.local`, `*.internal`, and `example.com/.net/.org/.edu`, all
reserved by IANA/ICANN under RFC 2606, RFC 6761 and RFC 6762. Claiming
`acme.example.com` cannot harm anyone, because there is no owner to harm and
there can never be one.

Consequences that fall out of that single rule:

- `SANDBOX` on a real domain is **refused**, in every environment, with any
  credentials. There is no path to sandbox-verifying `google.com`.
- A reserved name **cannot** use the live methods — it has no real website, so
  there is nothing to check.
- Eligibility is decided once, at creation, from the hostname alone, and stored
  immutably. A domain cannot drift between modes.
- Sandbox domains are labelled everywhere, and roll up to a business service
  mode of `TEST` with a persistent banner.

Alongside it, `DEV_BYPASS` for CI and local development — fail-closed,
boot-resolved, audited, and **structurally** indistinguishable from a typo in
production (§4.2).

This is the [Stripe test-mode](https://docs.stripe.com/test-mode) pattern
applied to domain ownership: a real, permanently available parallel path with
visibly different identifiers, rather than a special build or a support request.

### 4.2 Verification

**`common/security/sandbox-domains.ts` (new).** The eligibility classifier.
Every comparison is exact or on a `.`-prefixed suffix, so `example.com.evil.com`
and `notexample.com` — both ordinary domains an attacker can buy — cannot match.
A blank or malformed `SANDBOX_DOMAIN_SUFFIX` is rejected rather than degrading
into "matches everything", which a naive `endsWith('.' + suffix)` would do.

**`config/verification-methods.ts` (new).** The bypass gate, resolved once at
process boot from environment variables alone.

The important part is *how* it makes the bypass invisible. The obvious approach
— accept the value, then reject it later with a hand-crafted error mimicking a
validation failure — is a thing that can be got subtly wrong and must be
re-verified after every refactor. Instead, the gate decides **what the enum
is**. The DTO validates against `ACCEPTED_VERIFICATION_METHODS`, so in
production `DEV_BYPASS` is not a method that gets rejected — it is not a method,
and it is refused by the same ValidationPipe, on the same line, with the same
422 body, as `HAMSTER`. Indistinguishability is structural, not maintained.

A production process configured with the bypass enabled now **refuses to boot**
(`main.ts`), so the misconfiguration is loud at deploy time instead of silent
forever.

**`domain-verification.service.ts` (rewritten).**

| Change | Why |
|---|---|
| DNS record name → `_replyiq-verification.{domain}`, legacy `_replyiq-challenge` still accepted | Matches the meta tag's attribute name; nobody's published record breaks |
| TXT records compared **individually**, then jointly | **Bug fix.** The old code joined every chunk of every record into one string, so a correct record failed whenever a second unrelated TXT record existed at the same name — routine during a DNS provider migration |
| Website method now genuinely parses `<meta name="replyiq-verification">` | The enum was called `HTML_META` and checked a file. Attribute order, quoting style, case and minification all tolerated |
| `/.well-known/replyiq-verification.txt` and the legacy `/replyiq-verification.html` accepted as equivalent | A CMS user has a header box and no filesystem; a static-site user has the opposite. One method, three routes |
| HTTPS attempted before HTTP | **Security fix.** Fetching `http://` only is a downgrade by default: it invites a network attacker to answer for an HTTPS-only site, and fails outright on sites that reject plaintext |
| Three outcomes: `VERIFIED` / `MISMATCH` / `PENDING` | Was two. "Not found yet" and "found but wrong" have different causes and different fixes |
| Body cap 64 KB → 512 KB | 64 KB truncated real homepages before reaching a meta tag late in a large `<head>` |
| Scheme remembered after the first answer | A plaintext-only site was costing three wasted TLS handshakes before the fallbacks were reached |
| Test fixture hook reworked to substitute the dial target | **Bug fix.** The previous hook substituted a hostname that then had to survive `resolvePinnedAddress`, which correctly rejects loopback — so it could never have reached a local fixture server. The hook was unusable as written |

**`domain.service.ts` (rewritten).** Method dispatch with eligibility gating,
audit on every lifecycle event, `lastCheckedAt`, derived service mode, and the
new delete semantics.

**`common/guards/org-throttler.guard.ts` (new).** Rate limits keyed on the
authenticated organization rather than the IP. The abuse being prevented is one
tenant driving the verify endpoint to make the server issue outbound requests;
that tenant controls its own IP, while a shared office NAT would penalise
unrelated tenants for each other's usage.

**`infrastructure/audit/` (new).** Append-only lifecycle log. Writes never
throw — losing an audit line is preferable to failing a verification the user
legitimately completed — and the failure still reaches the application logger.
The verification token is never written to it.

### 4.3 Elsewhere

| Change | Why |
|---|---|
| `INTERNAL_ERROR` code added and emitted for every 500 | Found by the new error-copy contract test: a 500 carried no code, so the client lost the one thing worth saying — that the user did not cause it |
| Register response wrapped in `{ success, message, data }` | It was the only endpoint returning a bare object, permanently forcing every client to special-case exactly one shape. Both sides changed together (D-03R) |
| `Business.serviceMode` exposed, derived per read | A stored flag would need updating on create, verify, delete and soft-delete — four chances to drift. A computed value cannot be wrong |
| `CreateDomainDto` hostname pattern `*` → `+` | **Bug fix.** The old pattern also matched single-label strings, so `com` was a valid domain and could take a global uniqueness claim on a bare TLD |
| Input normalisation accepts pasted URLs | `https://www.acme.com/pricing` and `acme.com` are the same claim |

## 5. Web

### 5.1 The error-copy contract

`api/error-copy.ts` (new) is the single place a machine code becomes words. The
backend `message` is never rendered; it exists for logs.

`common/errors/error-copy-contract.test.ts` (API side) reads the client's copy
table and fails the build if the API can emit a code the client has no words
for — or if the client carries copy for a code that no longer exists. Goal G4
is now enforced rather than intended.

### 5.2 Design system

`index.css` defines brand and ink palettes as Tailwind v4 `@theme` tokens, one
keyboard-only focus treatment, monospace with ligatures off (users compare these
values character by character), and a global `prefers-reduced-motion` rule.

New and rebuilt components: `Banner` / `ErrorBanner` (icon + wording per tone,
so meaning survives greyscale and colour-vision deficiency), `CopyField`
(never truncates — an ellipsis silently produces a wrong paste — with a
clipboard fallback for plain-HTTP origins), `Modal` (focus trap, focus restore,
labelled dialog, mobile sheet), `Stepper`, `Badge` (distinct violet for Test),
`Skeleton`, `EmptyState`, `AuthShell`, `PasswordRequirements`.

### 5.3 Screens

## 6. Decisions superseded

| Was | Now | Why |
|---|---|---|
| **D-01** — file-only verification; meta tag rejected | **D-01R** — meta tag first, file placements as equivalent alternatives | D-01 chose the file because that is what the code did. That is a description of the present, not a product decision. The meta tag is what a non-technical user can actually place |
| **D-03** — keep the register response un-enveloped until a breaking window | **D-03R** — enveloped now | We control both sides; deferring it only extended a permanent papercut |
| **D-04** — implement no bypass; use a real staging subdomain | **D-04R** — Test Mode in production, `DEV_BYPASS` for non-production | A staging subdomain cannot run offline and makes CI depend on a shared DNS zone. | **D-06** — block deleting the last verified domain | **D-06R** — allow with explicit acknowledgement | Blocking stranded anyone who verified the wrong domain. A hard "no" on the user's own data is a worse answer than a clear "are you sure" — and the acknowledgement is enforced on the API, so the safety survives outside the UI |
| **`OWNER/ADMIN/MEMBER/VIEWER`** proposed in external review | **`OWNER/ADMIN/MANAGER`** retained | The proposal named roles the data model does not have. Changing it is a schema migration, not a documentation edit |

## 11. Critical fix: the address pin broke every HTTPS fetch

Found while extracting `SafeHttpService`, after the verification path had
already shipped. Two defects, both of which looked like success from outside.

### 11.1 Certificate validated against an IP

To stop DNS rebinding, the code resolved the hostname, checked the address was
not in a reserved range, then connected to that address by **rewriting the URL's
hostname to the IP** and putting the real hostname in the `Host` header.

For HTTPS this cannot work. TLS validates the certificate against whatever is in
the URL, so it compared the certificate to an IP address, which never matches:

```
fetch failed | cause: ERR_TLS_CERT_ALTNAME_INVALID
```

The verification path deliberately collapses every network failure to
`PENDING` - it must not tell a requester why a host did not answer. So this
did not surface as an error. It surfaced as a domain that simply never
verified, for **every HTTPS site**, which is to say every real site. Website
verification had never once worked in production.

**Fix.** Pin at the DNS layer instead of the URL layer: keep the real hostname
in the request so SNI, certificate validation and `Host` are all correct, and
override the `lookup` option so the socket can only go to the address already
validated. This required moving from `fetch` to `node:http(s)`, which is the
only one of the two that exposes `lookup`. (`undici`'s `Agent` would also work
but is not importable under pnpm's strict layout.)

### 11.2 A pooled socket bypassed the pin entirely

With `lookup` in place, a deliberately mis-pinned control request - aimed at
`127.0.0.1` but asking for a public host - **still reached the real host**. Node's
global agent had pooled a keep-alive socket from an earlier request and reused
it, so `lookup` was never consulted.

A pin that can be skipped by a warm connection is not a pin. Every request now
sets `agent: false`.

### 11.3 Proof

Verified against a live host rather than a mock, because both defects were
invisible to mocked transport:

| Case | Before | After |
|---|---|---|
| HTTPS to a real host | `ERR_TLS_CERT_ALTNAME_INVALID` | `200`, certificate `*.iana.org`, socket on the resolved address |
| Request pinned to a dead address | succeeded against the real host | `ECONNREFUSED` |

Both properties are now regression-tested in
`safe-http.service.test.ts`, and both tests were confirmed to **fail** when each
defect is reintroduced - a test for a silent bug is worthless unless it is shown
to break. The socket-level assertions run against the service's own exported
`buildPinnedRequestOptions`, not a copy of the options, so dropping `agent:
false` from the shipped code fails the suite.

### 11.4 Related regression caught in passing

The CORS registration block had been lost from `main.ts` in the working tree
(the import remained, which is what surfaced it via lint). Restored from the
committed version. Left unnoticed it would have blocked the deployed dashboard
from calling the API at all.
