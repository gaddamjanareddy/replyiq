# ReplyIQ - Database Specification

> Defines the complete data model for ReplyIQ. All tables, columns, types, constraints, indexes, relationships, migrations, and seed data. Authoritative source for schema decisions.

## 1. Overview

ReplyIQ uses **PostgreSQL 17** as its primary data store, accessed through **Prisma 6.6** ORM. The database is organized as a multi-tenant system where all business data is scoped to an `organizationId` foreign key.

### 1.1 Current State

| Metric | Value |
|--------|-------|
| Database Engine | PostgreSQL 17 |
| ORM | Prisma 6.6 |
| Total Enums | 7 |
| Total Models | 6 (implemented) |
| Total Migrations | 3 |
| Primary Key Type | UUID (all models) |
| Soft Delete Models | 4 of 6 |

### 1.2 Conventions

| Convention | Rule |
|------------|------|
| **Primary Keys** | UUID v4, generated by `uuid()` (Prisma) or `gen_random_uuid()` (PostgreSQL) |
| **Table Naming** | Snake_case, plural (e.g., `organizations`, `business_domains`) |
| **Column Naming** | camelCase in Prisma schema; snake_case in SQL (Prisma maps automatically) |
| **Timestamps** | `createdAt` (default `now()`), `updatedAt` (default `@updatedAt`), `deletedAt` (nullable, for soft delete) |
| **Foreign Keys** | Named as `{modelName}Id` in Prisma; `{table}_{column}_fkey` in SQL |
| **Indexes** | Named as `{table}_{column}_idx`; unique constraints as `{table}_{column}_key` |
| **Enum Naming** | PascalCase in Prisma; PostgreSQL native enum types |
| **DateTime Precision** | `TIMESTAMP(3)` (millisecond) for most columns; `TIMESTAMPTZ` for onboarding progress timestamps |
| **Cascade Rules** | `Restrict` on core entity ownership; `Cascade` on dependent records (sessions, onboarding) |

| Value | Description |

| `sessions_pkey` | `id` | Primary Key | Row lookup |

#### Business Rules

- Refresh tokens are stored as argon2 hashes, never plaintext.
- Each refresh token is single-use. On rotation (`SessionService.rotateRefreshToken`), the `refreshTokenHash` on the **existing session row is replaced** â€” no new row is created and `revokedAt` stays null. (Earlier revisions of this spec described revoke-and-recreate rotation; the implementation is hash-replacement in place.)
- A user can have multiple active sessions (multi-device support).
- Logout sets `revokedAt`; it does not delete the row. Cleanup of expired/revoked rows by a periodic job is planned but not implemented.

## 8. Tenant Isolation

### 8.1 Strategy

ReplyIQ enforces tenant isolation at the **application layer** through mandatory `organizationId` filtering on all queries.

### 8.2 Isolation Rules

| Rule | Implementation |
|------|----------------|
| **All queries scoped to organization** | Every database query for user, business, or domain data must include `WHERE organizationId = <current_org>` |
| **JWT contains organizationId** | The access token payload includes the user's `organizationId`, extracted by the auth guard |
| **No cross-organization access** | Users can never access data belonging to another organization, regardless of role |
| **Admin can only see their org** | Even platform administrators are scoped to their organization |
| **Soft delete respects isolation** | Soft-deleted records are excluded from queries via `deletedAt IS NULL` filter |

### 8.3 Query Pattern

```typescript
// Correct: Scoped to organization
const businesses = await prisma.business.findMany({
  where: {
    organizationId: request.user.organizationId,
    deletedAt: null,
  },
});

// Incorrect: No organization scope (data leak risk)
const businesses = await prisma.business.findMany({
  where: { deletedAt: null },
});
```

### 8.4 Session Isolation

Sessions are the only model without an `organizationId` column. They are isolated through the `userId` foreign key, which itself belongs to a specific organization. Session queries are always scoped to the authenticated user.

## 9. Soft Deletion Strategy

### 9.1 Models With Soft Delete

| Model | Column | Type |
|-------|--------|------|
| Organization | `deletedAt` | TIMESTAMP(3), nullable |
| User | `deletedAt` | TIMESTAMP(3), nullable |
| Business | `deletedAt` | TIMESTAMP(3), nullable |
| BusinessDomain | `deletedAt` | TIMESTAMP(3), nullable |

### 9.2 Models Without Soft Delete

| Model | Deletion Strategy | Rationale |
|-------|-------------------|-----------|
| Session | Hard delete via `Cascade` or expiration cleanup | Sessions are ephemeral, no recovery needed |
| OnboardingProgress | Hard delete via `Cascade` | Dependent on business, no independent value |

### 9.3 Soft Delete Rules

| Rule | Detail |
|------|--------|
| **Setting** | `deletedAt` is set to `now()` when a record is soft-deleted |
| **Querying** | All read queries must filter `deletedAt IS NULL` |
| **Updating** | Soft-deleted records should not be updated (enforced at application layer) |
| **Restoring** | A soft-deleted record can be restored by setting `deletedAt = null` |
| **Permanent deletion** | Soft-deleted records can be permanently removed by a periodic cleanup job (planned) |
| **Foreign keys** | Soft deletion does not affect foreign key constraints. A soft-deleted parent still prevents hard deletion of children via `ON DELETE RESTRICT` |

### 9.3.1 Unique Constraints vs Soft Delete - RESOLVED (APPROVED D-02)â€” Known Interaction [DECISION REQUIRED]

`BusinessDomain.domain` carries a **global** `@@unique([domain])` constraint that includes soft-deleted rows (there is no partial index on `deletedAt IS NULL`). Consequence, as implemented in `DomainService.create`: re-adding a domain name whose previous row was soft-deleted raises Prisma `P2002` â†’ API returns `409 Conflict "Domain already registered"` **even though no active domain uses the name**.

RESOLVED (APPROVED D-02, tracked in 15-ROADMAP.md): **Option 1 is approved.** The global `business_domains_domain_key` unique index is replaced by a **partial unique index** on active rows only:

```sql
CREATE UNIQUE INDEX "business_domains_domain_active_key"
  ON "business_domains"("domain")
  WHERE "deletedAt" IS NULL;
```

This is a deliberate hand-maintained SQL migration because Prisma DSL cannot express partial indexes; the schema must NOT silently recreate a full-table unique constraint (see migration `20260822000000_domain_partial_unique`). Soft-deleted domain names become re-registrable by any organization while audit history is preserved. `DomainService.create` pre-checks active rows only and additionally maps Prisma `P2002` to `409 DOMAIN_ALREADY_REGISTERED` for race safety.

Related: APPROVED D-06 adds concurrency-safe protection so a COMPLETED business cannot delete its last active VERIFIED domain (stable code `DOMAIN_LAST_VERIFIED`); legitimate business archival remains unaffected.

### 9.4 Prisma Filter Pattern

```typescript
// Find only non-deleted records
await prisma.business.findMany({
  where: { deletedAt: null },
});

// Find including soft-deleted records (admin recovery)
await prisma.business.findMany({
  where: { deletedAt: { not: null } },
});
```

## 10. Data Lifecycle

### 10.1 Record States

```
                +--------------+
                |   Created    |
                | (new record) |
                +------+-------+
                       |
                +------v-------+
          +-----|   Active     |-----+
          |     |  (normal)    |     |
          |     +------+-------+     |
          |            |             |
  Soft    |     +------v-------+     |  Hard
  Delete  |     |  Suspended   |     |  Delete
          |     |  (locked)    |     |  (cleanup)
          |     +------+-------+     |
          |            |             |
          |     +------v-------+     |
          |     |  Archived    |     |
          |     |  (permanent) |     |
          |     +--------------+     |
          |            |             |
          v            v             v
    +-------------------------------------+
    |          Soft Deleted               |
    |       (deletedAt set)               |
    |   - Recoverable                     |
    |   - Excluded from normal queries    |
    |   - Permanent cleanup after N days  |
    +-------------------------------------+
```

### 10.2 Lifecycle Per Model

| Model | States | Transitions |
|-------|--------|-------------|
| **Organization** | ACTIVE -> SUSPENDED -> ARCHIVED | Managed via admin API |
| **User** | INVITED -> ACTIVE, ACTIVE -> DISABLED | Invitation acceptance, admin action |
| **Business** | DRAFT -> ACTIVE, ACTIVE -> SUSPENDED -> ARCHIVED | APPROVED (D-05): DRAFT->ACTIVE happens atomically inside the onboarding COMPLETE transaction (no partial updates). Suspension/archival: admin API planned. NOTE: business archival must remain possible even when domains exist (D-06 exception) |
| **BusinessDomain** | PENDING -> VERIFIED, any -> DISABLED | Domain verification, admin action |
| **Session** | Active (expiresAt in future) -> Revoked | Login, logout, token rotation, expiry |
| **OnboardingProgress** | Steps completed sequentially | Profile -> Domain added -> Domain verified -> Complete |

### 10.3 Cleanup Schedule (Planned)

| Operation | Frequency | Target |
|-----------|-----------|--------|
| Expired session removal | Daily | Sessions where `expiresAt < now()` |
| Revoked session removal | Weekly | Sessions where `revokedAt < now() - 30 days` |
| Permanent soft-delete cleanup | Monthly | Records where `deletedAt < now() - 90 days` |
