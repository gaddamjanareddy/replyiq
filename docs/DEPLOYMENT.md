# Deploying ReplyIQ

> First deployment: everything on Render, free plan, from `render.yaml`.

**Status:** ready to deploy · **Last updated:** 2026-09-05

---

## What you get

Three services, created from one blueprint file and wired to each other:

| Service | What it is | Plan |
|---|---|---|
| `replyiq-db` | PostgreSQL 17 | free |
| `replyiq-api` | NestJS API | free |
| `replyiq-web` | React dashboard (static) | free |

You end up with `https://replyiq-web.onrender.com` for the dashboard and
`https://replyiq-api.onrender.com` for the API.

---

## Before you start — read this bit

The free plan has two consequences that will surprise you otherwise:

1. **The API sleeps after ~15 minutes idle**, and the next request cold-starts
   it in roughly 50 seconds. The dashboard will look broken for that first
   request. Fine for evaluation, not for anyone you're trying to impress.
2. **The free database is deleted 30 days after creation.** There is then a
   14-day grace period in which upgrading to a paid plan keeps your data. Free
   databases also have **no backups at all**.

So: run `./scripts/backup-db.sh` before you care about anything in there, and
upgrade the database (~$7/month) the moment a real business signs up. Upgrading
is a plan change in the dashboard — no code change, no redeploy, no data loss,
as long as you're inside the window.

**Put a reminder in your calendar for 30 days after you create the database.**

## Deploy

### 1. Push the branch and merge it

Render deploys from a branch, so the work has to be on GitHub first.

### 2. Create the blueprint

In Render: **New → Blueprint**, connect `smartfindshub/replyiq`, pick the
branch. Render reads `render.yaml` and shows you the three services it will
create. Click apply.

That's the whole thing. Specifically, you do **not** need to:

- type any URLs — the API's `CORS_ORIGINS` and the dashboard's `VITE_API_URL`
  are composed from each other's hostnames at deploy time;
- create secrets — `JWT_SECRET` and `JWT_REFRESH_SECRET` are generated by
  Render and never appear in git;
- run migrations — the API's start command runs `prisma migrate deploy`, which
  is idempotent and forward-only.

### 3. Check it came up

```bash
curl https://replyiq-api.onrender.com/api/v1/health
# {"status":"ok","service":"replyiq-api","version":"0.1.0"}
```

Then open the dashboard, create a workspace, and add a test website like
`my-business.example.com`. It verifies instantly, so you can confirm the whole
funnel end to end without owning a domain — including in production.

## If something goes wrong

| Symptom | Cause |
|---|---|
| Build fails on `pnpm install` | `NODE_VERSION` isn't 22, or `pnpm-lock.yaml` is out of date. Run `pnpm install` locally and commit the lockfile. |
| API boots then exits immediately | Look for `FATAL: ALLOW_DEV_VERIFICATION_BYPASS=true is set with NODE_ENV=production`. That's the guard doing its job — set it to `false`. |
| Dashboard loads, every request fails | `VITE_API_URL` is baked in at **build** time. If you change it, you must redeploy the static site, not just restart it. |
| CORS errors in the browser console | `CORS_ORIGINS` must be the **full origin** (`https://replyiq-web.onrender.com`), not a bare hostname. Do not use `fromService … property: host` for it — that returns the internal service name, and the API will answer `access-control-allow-origin: https://replyiq-web`, which matches nothing. |
| Sign-up works but the wizard won't advance | A PATCH being blocked by CORS. The allowed methods are declared explicitly in `main.ts`; if they ever get dropped, the preflight advertises only `GET,HEAD,POST` and every onboarding step fails while login still looks fine. |
| First request takes ~50 seconds | The free service was asleep. Expected. |
| `P1001: Can't reach database` | The database is still provisioning, or it expired. Check its status. |

## Going to production properly

The free deployment is a private beta, not a launch. Before real businesses
depend on it:

| Blocker | Why it matters |
|---|---|
| **No password reset, no email verification** | A user who forgets their password is locked out permanently, and you'd be fixing it by hand in the database. Needs an email provider. |
| **Tokens in `localStorage`** (NFR-SEC-09) | Should be httpOnly cookies before real customer sessions. |
| **Rate limiting is in-memory** | Correct on one instance. Add Redis before scaling to more than one. |
| **No error tracking** | Wire Sentry, or you'll learn about failures from users. |
| **Paid database** | For backups, and so it doesn't get deleted. |
| **Privacy policy, terms, DPA** | You'd be storing other companies' data. |
| **The product itself** | Knowledge engine, AI receptionist and widget are Milestones 5–7 and don't exist yet. A business can sign up and verify a domain — and then nothing happens. |

## Backups

```bash
./scripts/backup-db.sh "$(render-external-database-url)"
```

Get the external URL from **replyiq-db → Connect → External Database URL**.
Dumps land in `backups/` (gitignored) and the last 14 are kept. Restore with:

```bash
gunzip -c backups/replyiq-YYYYmmdd-HHMMSS.sql.gz | psql "<target-url>"
```

## Local development

```bash
docker compose up -d postgres
pnpm install
pnpm --filter @replyiq/database exec prisma migrate deploy
pnpm --filter @replyiq/database exec prisma db seed
pnpm dev
```

> **CORS is not exercised locally.** The Vite dev server proxies `/api` to the
> API, so the browser only ever talks to one origin. Cross-origin behaviour —
> allowed origins, allowed methods, preflight — is first exercised in a deployed
> environment, and has broken there while every local test passed. When you
> change anything CORS-related, verify it against the deployed URL:
>
> ```bash
> curl -sD - -o /dev/null -X OPTIONS >   -H "Origin: https://replyiq-web.onrender.com" >   -H "Access-Control-Request-Method: PATCH" >   https://replyiq-api.onrender.com/api/v1/businesses/x | grep -i access-control
> ```

Dashboard on `http://localhost:5173`, API on `http://localhost:3000`. To reach
it from your phone, start the dashboard with `pnpm --filter @replyiq/web dev --host`
and open `http://<your-lan-ip>:5173` — the Vite dev server proxies `/api` to the
API, so no CORS configuration is needed.
